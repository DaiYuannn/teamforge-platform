# 小团队反馈归纳与版本改造说明

> 适用分支：`codex/personal-small-team`
>
> 整理日期：2026-07-29
>
> 目的：将口头反馈转化为明确的产品规则、实现范围和验收标准。

## 1. 总体判断

这批反馈集中反映的不是单个页面缺字段，而是当前系统仍以“一个大团队、单一负责人、内部成员近似全员互见”为基础。个人小团队版本应改为：

```text
总实践团队
├─ 小团队 A：1 名主负责人 + 多名共同负责人 + 成员
├─ 小团队 B：1 名主负责人 + 多名共同负责人 + 成员
└─ 小团队 C：1 名主负责人 + 多名共同负责人 + 成员

项目、比赛、知识产权成果可以跨小团队协作，不重复建档。
普通成员只看到与本小团队或本人项目有关的内部内容。
五名学生核心成员按职责管理，老师只处理被明确指定的事项。
```

本次改造坚持四个原则：

1. 组织归属、项目参与和具体任务责任分开记录；
2. 一个项目或成果可以关联多个小团队，但只保留一份档案；
3. 敏感信息必须按小团队和用途授权，不能因为是老师或系统管理员就默认全可见；
4. 不用填报时长替代工作质量、有效产出和任务验收。

## 2. 反馈归纳与处理结论

### 2.1 总团队与小团队

反馈问题：

- 现在只能看到一个大团队中的所有人，看不出成员具体属于哪个小团队；
- “转为负责人”到底是增加一名负责人，还是把原负责人替换掉，不清楚；
- 一个小团队可能同时由多人负责。

处理结论：

- 团队改为“总实践团队—小团队”两级结构；
- 每个小团队保留一名“主负责人”，用于数据归属和最终交接；
- 允许多名“共同负责人”，共同负责人可以管理本小团队成员和业务；
- “设为共同负责人”和“转让主负责人”必须是两个不同操作；
- 同一成员可以参加多个小团队，不把小团队归属做成用户表上的单一字段。

### 2.2 成员档案

反馈问题：

- 成员信息缺少学校；
- 需要看到所属小团队、参与项目、比赛和具体工作；
- 团队负责人需要在成员详情中继续处理角色。

处理结论：

- 成员档案增加学校；
- 成员列表和详情显示全部有效小团队及组内角色；
- 成员详情继续显示项目、比赛、任务和贡献记录；
- 从团队成员行可以直接进入成员详情；
- 身份证号不加入普通成员接口，避免通过人员列表泄露。

### 2.3 身份证和敏感资料

反馈问题：

- 身份证号在哪里查看不明确；
- 本小团队负责人、材料整理人和知识产权申请执行人可能需要使用；
- 其他小团队不应看到；
- 团队 PPT、计划书和身份证的敏感程度不同。

处理结论：

- 身份证继续使用加密的敏感资料模块，不在用户表保存明文；
- 敏感资料增加“资料本人”和“所属小团队”，上传人不再等同于资料本人；
- 其他小团队连该身份证的脱敏目录都不应看到；
- 本小团队主负责人、共同负责人和被明确授权的资料经办人可按用途查看；
- 每次明文查看仍需记录用途、有效期和审计日志，身份证默认禁止下载；
- PPT、计划书优先放入限定小团队或项目范围的文件中心，不与身份证使用同一套默认审批。

### 2.4 项目与跨团队协作

反馈问题：

- 一个人可能负责多个项目；
- 一个软件、软著或成果可能同时服务多个小团队；
- 如果分别归到两个负责人名下，会产生重复项目；
- “负责人”可能指小团队负责人、项目负责人或任务负责人。

处理结论：

- 项目保留一名“项目牵头负责人”，同时允许多名“项目共同负责人”；
- 项目可以关联多个小团队，不再为跨团队协作重复建档；
- 本轮未增加“小团队主责/协作”关系类型，需要时先在项目责任说明中记录，结构化标注列入后续增强；
- 一个跨团队项目只建立一次；
- 页面统一使用明确术语：
  - 小团队主负责人；
  - 小团队共同负责人；
  - 项目牵头负责人；
  - 项目共同负责人；
  - 比赛负责人；
  - 任务负责人；
  - 协作执行人；
  - 验收人；
  - 子任务执行人。

### 2.5 项目可见范围

反馈问题：

- “公开”和“内部”究竟指互联网、整个实践团队还是一个小团队，不清楚；
- 项目分工等内容可能不希望其他小团队看到；
- 不是所有内容都需要展示。

处理结论：

项目提供三种登录后可见范围：

| 范围 | 可见人 |
|---|---|
| 仅项目成员 | 项目牵头负责人、共同负责人和活动项目成员 |
| 关联小团队 | 项目成员及项目关联小团队的活动成员 |
| 全实践团队 | 所有仍在队或暂离的内部成员 |

互联网公开不使用上述范围。互联网公开必须在“公开门户”中逐项开启；成员资料还需本人授权。未逐项开启的内容不会出现在无需登录的页面。

文件权限目标文案统一为：

- 同一实践团队登录成员可见；
- 仅本项目成员；
- 敏感资料（申请或授权后可见）。

本轮先完成根实践团队隔离和项目成员隔离；独立的“仅指定小团队”文件级仍列为后续增强。

### 2.6 比赛管理

反馈问题：

- 比赛详情目前更像比赛信息整理；
- 看不到实际参加的负责人和团队成员；
- 临时比赛数量多，不能只靠项目负责人记忆。

处理结论：

- 比赛增加独立参赛名单；
- 每名参赛者记录比赛角色、计划/确认/退出状态和具体责任；
- 比赛详情直接显示比赛负责人、核心成员和普通参赛成员；
- 获奖人名单不能替代参赛名单；
- 比赛名单默认从关联项目的活动成员中选择。

### 2.7 任务与有效工作

反馈问题：

- “负责人”含义不清；
- 只看到负责人会让其他成员的工作不可见；
- 管理者需要判断任务是否真正有效。

处理结论：

- 任务本身已有任务负责人、协作者、验收人和子任务执行人，不重复新增模型；
- 修改页面名称并同时展示上述责任人；
- 本轮所有任务仍沿用“提交验收—验收人确认有效完成或退回继续”的统一闭环；
- 后续可增加“无需验收”开关，仅让正式交付、关键里程碑、高风险或对外提交任务强制验收；
- 贡献评价以验收结果、交付质量和实际效果为依据，不以填报小时数直接换算。

### 2.8 可投入安排

反馈问题：

- 成员更愿意填写某段日期内是否有时间，例如 22 日至 24 日约可投入一天半；
- 不希望工作完成后再补详细工时；
- 投入时间长不等于贡献大。

处理结论：

- “灵活工时”改名为“可投入安排”；
- 填写日期窗口、约可投入半天数、是否能线下、是否能接紧急任务和备注；
- 只做排期参考，不要求补录实际工作时长；
- 工时字段仅为历史兼容，不在新界面中作为核心指标展示；
- 贡献分值不得直接由填报时长生成。

### 2.9 经费、预算、报销和付款

反馈问题：

- “待审核、已审核、已付款”无法判断钱处于哪一步；
- 不清楚是先允许花钱，还是花钱后审核报销；
- 希望看到预计可花多少钱、已经花了多少，避免超支；
- OCR 不应是唯一登记入口。

处理结论：

报销状态改用明确文案：

```text
草稿
→ 待报销审核
→ 审核通过，待打款
→ 已打款，报销完成
```

- “审核通过”只表示票据和用途通过，不等于钱已到账；
- “已打款”表示已经向成员报销或向供应方完成付款；
- 经费总览分开显示核定预算、累计入账、已完成付款、审核中/待付款占用和可用额度；
- 草稿和已驳回记录不占用预算；
- 增加手工新增支出，OCR 只是可选的票据识别工具；
- 大额、预算外或学校经费以后可继续接入用款前申请。

### 2.10 知识产权和成果

反馈问题：

- 需要清楚看到成果具体有哪些参与人；
- 实际工作贡献人与法律申报名单不是一回事；
- 姓名和身份证不匹配时，需要知道最终是继续、退回还是终止；
- 一个成果可能服务多个项目。

处理结论：

- 保留现有工作贡献人和责任分工；
- 另增“拟申报名单”，记录申报身份、拟署名顺序、实名核验状态和最终提交状态；
- 身份证号只从受保护的成员身份资料核验，不复制到知识产权表；
- 成果可以关联多个项目，并指定主项目；
- 暂停、转后续申请和终止必须填写原因；
- 列表与详情明确显示“正在办理、退回修改、已受理、已授权、暂停、转后续、已终止”等状态。

### 2.11 贡献审核

反馈问题：

- 手工添加贡献需要审核；
- 如果只有一个项目负责人审核，负责人会很累；
- 负责人自己的贡献需要无利益关系的人复核；
- 希望可以由其他负责人或其他小团队成员协助。

处理结论：

- 本轮知识产权责任确认已可形成带来源证据的已确认贡献；
- 任务验收、比赛确认名单自动形成已确认贡献仍列为后续增强；
- 手工贡献分派给项目配置的贡献审核人；
- 申请人不能审核自己的贡献；
- 项目牵头负责人自己的贡献必须改派给无利益关系的审核人；
- 老师不再默认收到全团队贡献审核；
- 批量审核仅用于同项目、同来源、无冲突的记录。

### 2.12 导入中心与资料文件

反馈问题：

- 导入中心为什么只支持 Excel 和 CSV；
- 证件照、PPT、文档等其他文件如何处理。

处理结论：

- 导入中心继续只处理具有行列结构的数据；
- Excel/CSV 用于批量导入成员、项目、比赛、任务、经费和知识产权档案；
- 普通照片、PPT、Word、PDF、压缩包进入文件中心；
- 身份证、签名、银行卡和敏感证件进入敏感资料；
- 页面增加两个清晰入口，不让用户误以为所有文件都必须转换成 Excel；
- 成员导入模板增加学校和目标小团队编号。

### 2.13 公告、知识沉淀和会议回放

反馈问题：

- 希望整理常见问题、计划书/PPT问题、新闻和腾讯会议回放；
- 目前公告如果只显示标题，无法真正作为知识入口。

处理结论：

- 公告列表可以打开正文详情；
- 分类增加通知、常见问题、资料模板、会议回放和新闻；
- 支持附加资源链接；
- 发布范围区分全实践团队、指定小团队、指定项目和互联网公开；
- 小团队主负责人、共同负责人及获得公告管理权限的核心成员可以发布，不要求老师处理。

### 2.14 教师和负责人的默认工作视角

第二轮反馈问题：

- 教师看到很多项目时，不能快速判断项目属于哪个小团队、哪场比赛；
- “负责人”既可能是挂名指导人，也可能是实际把事情接下来执行的人；
- 小团队负责人最需要先看到自己团队的人在做什么，而不是先浏览整个实践团队；
- 如果固定页面仍然太杂，需要允许保留个人常用面板。

处理结论：

- 项目清单提供“我的小团队、我管理的、我参与的、全部可见”四个工作视角；
- 普通内部成员、负责人和已经关联团队的教师默认进入“我的小团队”；
- 教师指导总团队时，“我的小团队”包含该总团队下的直属小团队；
- 老教师账号若尚未建立团队关系，回退到其权限范围内的项目并明确提示，不显示误导性的空页面；
- 可以继续指定某个总团队或小团队筛选，并记住当前视角和筛选，作为个人常用面板；
- 页面分别显示小团队负责人、项目牵头负责人、项目共同负责人、比赛执行负责人，不再只写“负责人”。

### 2.15 项目内“每个人在做什么”

第二轮反馈问题：

- 只显示项目负责人会显得所有工作都由负责人完成；
- 负责人可能只是对外挂名，实际任务由其他同学承接；
- 需要同时看到成员的任务、协作工作、参赛分工和比赛结果。

处理结论：

- 项目清单可展开成员执行摘要；
- 每位活动成员分别显示主责任务数、协作任务数、当前进行中任务及最多三项当前任务标题；
- 同时显示成员参加的比赛和该成员在每场比赛中的具体责任；
- 比赛摘要显示实际比赛执行负责人、参赛人数和获奖结果；
- 这些数据来自任务和比赛执行记录，不根据项目负责人姓名推断。

### 2.16 比赛贡献与复用

第二轮反馈问题：

- 比赛信息之外，更重要的是哪些人实际参加、分别做了什么；
- 过去项目中的图表、材料或研究结果可能可以直接用于新比赛；
- 复用内容不能导致同一贡献被重复计算。

处理结论：

- 比赛详情按人展示实际参赛状态、比赛角色、具体责任和本比赛贡献；
- 本比赛分工与已审核贡献分开显示，不能把计划分工直接算成有效贡献；
- 可复用区只列出当前参赛成员在查看者可见项目中的记录；
- 只有“审核通过且来源已核验”的记录进入可复用区；
- 复用只引用内容和证明材料，原贡献继续归属来源项目，不自动复制、不重复计分；
- 私密项目中的贡献不会因为同一个人参加了当前比赛而泄露。

### 2.17 经费页面的阅读顺序

第二轮反馈问题：

- 相比一个可能由公式计算的“余额”，负责人更想先看已经花了多少钱；
- 需要直接回答哪个项目、谁经手、花在什么地方、是否报销完成；
- “余额”如果不是银行或学校系统的实时余额，不能让人误以为是真实账户金额。

处理结论：

- 经费首页按“已记录支出—报销进度—预算控制—计算可用额度”排序；
- 教师和负责人常看的项目清单同样先显示已记录支出，再显示计算可用额度；
- 增加“钱花在哪里”汇总，按项目列出支出总额、笔数、经手人、具体用途和报销状态；
- 支出结构按全部已记录支出计算，不只统计已经打款的记录；
- “余额”统一解释为系统计算的可用额度，并展示计算口径；
- 预算仍用于防止超支，但不再压过实际支出信息。

### 2.18 文件夹操作语义

第二轮反馈问题：

- “目录”不清楚是筛选、进入还是文件的真实保存位置；
- 需要明确区分进入文件夹、上传文件和新建文件夹。

处理结论：

- 文件页显示“项目—根目录—当前文件夹”的面包屑；
- 子目录卡片使用“进入”，进入本身不会上传文件；
- 上传按钮写明“上传到当前目录”，弹窗再次展示目标路径；
- 新建文件夹默认建在当前目录，按钮在子目录中改为“新建子文件夹”；
- 全部目录汇总视图中的上传和新建默认使用项目根目录；
- 后端保存并校验文件与所选文件夹的真实关联。

### 2.19 定时报表接收范围

第二轮反馈问题：

- 定时报表是不是每个人都会收到；
- 如果给全团队发送，会不会增加大量日常操作或泄露无权查看的项目。

处理结论：

- 定时报表不默认群发；
- 创建人可以逐个选择接收人，也可以一键选择当前可见团队全员；
- 接收人必须有权查看报表涉及的全部项目，否则不能保存该计划；
- 因此“全员接收”是一次明确选择，不会绕过项目权限。

### 2.20 贡献审核的工作量与可信度

第二轮反馈问题：

- 新成员自报工作后，如果只有负责人审核，可能既累又难判断是否有效；
- 负责人自己的贡献不能由自己确认；
- 又不希望所有负责人、老师或其他团队成员逐级会签。

处理结论：

- 一条手工贡献只分派给一名明确审核人，不走全员逐级审核；
- 每个项目配置审核人池，可以加入共同负责人、其他团队的可信成员或指定老师；
- 普通成员按审核池优先级分派；
- 项目负责人自报贡献时必须分派给独立审核人；
- 贡献人和代填人均不能审核该条记录；
- 审核关注交付物、来源证明和实际效果，不用填报时长替代质量判断。

## 3. 本次实现优先级

### P0：先解决结构和误解

1. 总实践团队—小团队层级；
2. 主负责人和共同负责人分开；
3. 学校和成员小团队归属；
4. 项目牵头负责人、任务负责人等术语；
5. 比赛参赛名单；
6. 经费状态和预算口径；
7. 可投入安排；
8. 公开、项目内和敏感三类文案。

### P1：收紧权限并支持跨团队协作

1. 项目关联多个小团队及项目可见范围；
2. 敏感资料所属人和所属小团队；
3. 身份证目录与审批队列隔离；
4. 工作台、待办和文件按项目/小团队过滤；
5. 知识产权多项目和拟申报名单；
6. 贡献审核分派与自我回避。

### P2：进一步降低人工负担

1. 自动贡献依据任务验收、比赛名单和知识产权责任确认直接生效；
2. 同类无冲突贡献批量审核；
3. 资金用款前申请；
4. 敏感资料临时授权、到期撤销及下载权限分离；

### 4.1 操作量变化

普通成员不会因为这次改造增加长审批链：

- 日常任务、公告阅读、可投入安排仍是直接填写或更新；
- 手工贡献、敏感资料查看和报销只多出一次必要提交；
- 不要求成员补录实际工时；
- 普通成员不需要先理解总团队、项目和任务的全部权限配置。

负责人增加的是初始或低频配置，以及每项业务必要的维护，不是把每件事项都送给全部负责人或老师：

- 初次建立总团队和小团队；
- 按项目选择关联小团队、可见范围和贡献审核池；
- 按比赛持续维护实际参赛名单；
- 按项目或预算期维护核定预算。

完成这些配置后，普通事项由对应负责人直接处理，不再逐级送给所有核心成员或老师。手工报销仍是“保存草稿—确认提交”两步，以避免未核对记录直接进入审核；其后只由业务审核人决定一次、付款经办人登记一次。老师日常不需要查看团队任务、普通贡献和普通公告；只有知识产权、学校经费、正式材料、敏感资料或明确指派事项才进入老师入口。

第二轮改造没有给普通成员增加新的固定步骤：

- 项目和比赛执行信息来自原有任务、参赛名单和贡献记录，只是集中展示；
- “我的小团队”是默认视角，负责人无需每次重新筛选整个实践团队；
- 报表全员接收是一个可选的“一键全选”，不是逐人重复添加，也不是默认群发；
- 进入文件夹、上传到当前目录、新建子文件夹分别只有一次明确操作；
- 贡献仍然只需一名无冲突审核人处理，不要求老师或多个负责人串行会签。

### 4.2 明确留到后续的增强项

以下内容不影响本轮小团队基本使用，但仍需单独设计：

- 文件中心增加独立的“仅指定小团队”文件级别；
- 大额或预算外事项的用款前申请；
- ZIP 文件配清单的批量资料导入；
- 无冲突贡献批量审核和更多系统证据自动确认；
- 普通任务“无需验收”开关；当前所有任务仍走统一验收闭环；
- 公告资源直接上传附件；当前资源采用链接。
