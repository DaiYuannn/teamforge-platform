# 小团队反馈归纳与版本改造说明

> 适用分支：`codex/personal-small-team`
>
> 整理日期：2026-07-29
>
> 目的：将口头反馈转化为明确的产品规则、实现范围和验收标准。

## 1. 总体判断

这批反馈集中反映的不是单个页面缺字段，而是当前系统仍以“一个大团队、单一负责人、内部成员近似全员互见”为基础。个人小团队版本应改为：

```text
总实践团队人员库（约 30 人，长期保存，不按比赛重复建人）
├─ 比赛届次 A
│  ├─ 项目甲 / 参赛队 1：负责人、成员、任务、最终工作量
│  └─ 项目乙 / 参赛队 2：负责人、成员、任务、最终工作量
└─ 比赛届次 B
   └─ 项目甲 / 参赛队 3：可复用同一人员和项目资料

固定小团队只用于长期管理或权限授权；实际参赛“组”由比赛届次与项目参赛条目共同确定。
项目、比赛、知识产权成果可以跨团队协作，不重复建档。
一个老师账号是全局“操作老师”，可处理全部业务；其余老师作为团队级“查看老师（只读）”。
学生负责人和核心贡献者按职责直接管理日常事项，不要求老师逐级审核。
```

本次改造坚持四个原则：

1. 组织归属、项目参与和具体任务责任分开记录；
2. 一个项目或成果可以关联多个小团队，但只保留一份档案；
3. 敏感信息必须按小团队和用途授权，不能因为是老师或系统管理员就默认全可见；
4. 不用填报时长替代工作质量、有效产出和任务验收。

## 2. 反馈归纳与处理结论

### 2.1 总人员库与比赛项目组

反馈问题：

- 总人员库需要保留所有人员，不能因为参赛分组而重复建档；
- 实际分组不是固定三个组，而是“比赛届次 × 项目参赛队”；
- 同一人可能同时参加多个比赛、多个项目参赛队；
- “转为负责人”到底是增加一名负责人，还是把原负责人替换掉，不清楚；
- 一个小团队可能同时由多人负责。

处理结论：

- 总实践团队继续作为全量人员库，默认按操作老师、负责人/核心成员、普通成员排序；
- 总人员库与每个组织成员列表均可按身份、学校、状态筛选；
- 比赛组织按比赛届次下拉，再按项目参赛条目显示负责人和成员配置；
- 添加参赛成员时从总人员库搜索，支持姓名、手机号、邮箱、学校、专业、角色、状态的任意片段，以及中文拼音、首字母、大小写和单字符；
- 同一成员可出现在多个参赛条目中，不重复创建用户；
- 固定小团队仍允许一名“主负责人”和多名“共同负责人”，用于长期管理、文件和敏感资料授权；
- “设为共同负责人”和“转让主负责人”必须是两个不同操作；
- “设为共同负责人”和“转让主负责人”是两个不同操作。

### 2.2 成员档案

反馈问题：

- 成员信息缺少学校；
- 需要看到所属小团队、参与项目、比赛和具体工作；
- 团队负责人需要在成员详情中继续处理角色。

处理结论：

- 成员档案增加学校；
- 成员列表和详情显示全部有效小团队及组内角色；
- 成员详情继续显示项目、比赛、任务和贡献记录；
- 从团队成员行可以直接进入成员详情；
- 身份证号不加入普通成员接口，避免通过人员列表泄露。

### 2.3 身份证和敏感资料

反馈问题：

- 身份证号在哪里查看不明确；
- 本小团队负责人、材料整理人和知识产权申请执行人可能需要使用；
- 其他小团队不应看到；
- 团队 PPT、计划书和身份证的敏感程度不同。

处理结论：

- 身份证继续使用加密的敏感资料模块，不在用户表保存明文；
- 敏感资料增加“资料本人”和“所属小团队”，上传人不再等同于资料本人；
- 其他小团队连该身份证的脱敏目录都不应看到；
- 本小团队主负责人、共同负责人和被明确授权的资料经办人可按用途查看；
- 每次明文查看仍需记录用途、有效期和审计日志，身份证默认禁止下载；
- PPT、计划书优先放入限定小团队或项目范围的文件中心，不与身份证使用同一套默认审批。

### 2.4 项目与跨团队协作

反馈问题：

- 一个人可能负责多个项目；
- 一个软件、软著或成果可能同时服务多个小团队；
- 如果分别归到两个负责人名下，会产生重复项目；
- “负责人”可能指小团队负责人、项目负责人或任务负责人。

处理结论：

- 项目保留一名“项目牵头负责人”，同时允许多名“项目共同负责人”；
- 项目可以关联多个小团队，不再为跨团队协作重复建档；
- 本轮未增加“小团队主责/协作”关系类型，需要时先在项目责任说明中记录，结构化标注列入后续增强；
- 一个跨团队项目只建立一次；
- 页面统一使用明确术语：
  - 小团队主负责人；
  - 小团队共同负责人；
  - 项目牵头负责人；
  - 项目共同负责人；
  - 比赛负责人；
  - 任务负责人；
  - 协作执行人；
  - 验收人；
  - 子任务执行人。

### 2.5 项目可见范围

反馈问题：

- “公开”和“内部”究竟指互联网、整个实践团队还是一个小团队，不清楚；
- 项目分工等内容可能不希望其他小团队看到；
- 不是所有内容都需要展示。

处理结论：

项目提供三种登录后可见范围：

| 范围 | 可见人 |
|---|---|
| 仅项目成员 | 项目牵头负责人、共同负责人和活动项目成员 |
| 关联小团队 | 项目成员及项目关联小团队的活动成员 |
| 全实践团队 | 所有仍在队或暂离的内部成员 |

互联网公开不使用上述范围。互联网公开必须在“公开门户”中逐项开启；成员资料还需本人授权。未逐项开启的内容不会出现在无需登录的页面。

文件权限目标文案统一为：

- 同一实践团队登录成员可见；
- 仅本项目成员；
- 仅指定小团队；
- 仅指定比赛参赛队；
- 敏感资料（申请或授权后可见）。

上述范围均已由后端保存和校验；其他小团队或其他参赛队不能只靠猜测 URL 查看或下载文件。

### 2.6 比赛管理

反馈问题：

- 比赛详情目前更像比赛信息整理；
- 看不到实际参加的负责人和团队成员；
- 临时比赛数量多，不能只靠项目负责人记忆。

处理结论：

- 比赛增加独立参赛名单；
- 比赛拆为“比赛届次”和“项目参赛条目”，同一届比赛可包含多个项目队伍，同一项目也可参加多届比赛；
- 每名参赛者记录比赛角色、计划/确认/退出状态和具体责任；
- 比赛详情直接显示比赛负责人、核心成员和普通参赛成员；
- 获奖人名单不能替代参赛名单；
- 比赛名单默认从关联项目的活动成员中选择。

### 2.7 任务、DDL 与有效工作

反馈问题：

- “负责人”含义不清；
- 只看到负责人会让其他成员的工作不可见；
- 管理者需要判断任务是否真正有效。

处理结论：

- 任务本身已有任务负责人、协作者、验收人和子任务执行人，不重复新增模型；
- 修改页面名称并同时展示上述责任人；
- 私聊确认后的任务、负责人、协作者、DDL 和完成说明登记到对应比赛参赛条目；
- 时间跨度和 DDL 仅作为参考，不能自动换算贡献；
- 需要验收的任务由独立验收人确认有效完成或退回继续；
- 贡献评价以验收结果、交付质量和实际效果为依据，不以填报小时数直接换算。

### 2.8 最终工作量占比与异议

反馈问题：

- 不需要成员持续填报详细灵活工时；
- 最终要公开的是每个比赛参赛队中各成员的有效工作量占比；
- 成员对占比有问题时应能提出异议。

处理结论：

- 系统以“比赛届次 × 项目参赛条目”为最小工作量核算范围；
- 负责人先保存草稿，完整覆盖有效参赛成员且合计 100% 后发布；
- 每人占比必须附理由，发布后全体参赛成员可见；
- 成员可提交异议，处理结果和时间线保留；
- 发布占比自动同步为带来源证据的已确认贡献，不因重复发布生成重复版本；
- 历史灵活工时数据仅保留兼容，不再作为新流程必填项。

### 2.9 经费、预算、报销和付款

反馈问题：

- “待审核、已审核、已付款”无法判断钱处于哪一步；
- 不清楚是先允许花钱，还是花钱后审核报销；
- 希望看到预计可花多少钱、已经花了多少，避免超支；
- OCR 不应是唯一登记入口。

处理结论：

经费首页改为“项目—比赛—参赛队资金追溯台账”，支出结构和计算余额下沉到分析区。主区支持两种等价视角：

```text
项目视角：一个项目参加多场比赛，每场比赛的奖金、垫付、预留和付款
比赛视角：一届比赛包含多个项目/参赛队，每个队的奖金、支出和待报销
```

- 一笔收入或支出可以直接关联参赛条目，也可以只登记一张主流水后分摊给同届比赛、同根组织下的多个项目参赛队，分摊合计必须等于主流水金额；
- 与比赛无关的费用明确进入“项目公共支出”，不会伪造比赛归属；
- 奖金分为“预计奖金、已确认应收、已到账”三阶段，只有已到账增加实际资金；
- 成员垫付时选择项目、比赛和参赛队，填写实际收款人并上传发票或原始票据；
- 提交后进入“待审核预留”，审核通过为“已审核待转账”，退回、驳回或撤回会释放预留；
- 付款可分多次登记；只有填写金额、收款人、付款时间、方式、流水号并上传转账凭证后，才计为“团队已支付”；
- 支持“部分支付、付款异常、冲正”，付款异常不计入实际支出；
- 学校先把钱发给老师或经办人时，使用“内部转付”；内部转付有独立凭证和动态，但不重复计算收入或支出；
- 经费总览分开显示实际到账、待审核预留、已审核待转账、团队实际支付、奖金待到账和当前可动用资金；
- 草稿和已驳回记录不占用预算；
- 增加手工新增支出，OCR 只是可选的票据识别工具；
- 日常流程保持为“成员提交—负责人审核—经费经办人付款”三个人工步骤；申请人或收款人不能审核自己的申请；
- 超额、跨项目、预算外、学校专项及知识产权费用可进入统一审批待办并由操作老师兜底处理。

### 2.10 知识产权和成果

反馈问题：

- 需要清楚看到成果具体有哪些参与人；
- 实际工作贡献人与法律申报名单不是一回事；
- 姓名和身份证不匹配时，需要知道最终是继续、退回还是终止；
- 一个成果可能服务多个项目。

处理结论：

- 保留现有工作贡献人和责任分工；
- 另增“拟申报名单”，记录申报身份、拟署名顺序、实名核验状态和最终提交状态；
- 身份证号只从受保护的成员身份资料核验，不复制到知识产权表；
- 成果可以关联多个项目，并指定主项目；
- 暂停、转后续申请和终止必须填写原因；
- 列表与详情明确显示“正在办理、退回修改、已受理、已授权、暂停、转后续、已终止”等状态。

### 2.11 贡献审核

反馈问题：

- 手工添加贡献需要审核；
- 如果只有一个项目负责人审核，负责人会很累；
- 负责人自己的贡献需要无利益关系的人复核；
- 希望可以由其他负责人或其他小团队成员协助。

处理结论：

- 本轮知识产权责任确认已可形成带来源证据的已确认贡献；
- 比赛参赛队最终工作量发布后自动形成带来源证据的已确认贡献；
- 手工贡献分派给项目配置的贡献审核人；
- 申请人不能审核自己的贡献；
- 项目牵头负责人自己的贡献必须改派给无利益关系的审核人；
- 老师不再默认收到全团队贡献审核；
- 批量审核仅用于同项目、同来源、无冲突的记录。

### 2.12 导入中心与资料文件

反馈问题：

- 导入中心为什么只支持 Excel 和 CSV；
- 证件照、PPT、文档等其他文件如何处理。

处理结论：

- 导入中心继续只处理具有行列结构的数据；
- Excel/CSV 用于批量导入成员、项目、比赛、任务、经费和知识产权档案；
- 普通照片、PPT、Word、PDF、压缩包进入文件中心；
- 多份人员资料可使用 ZIP 加清单批量导入；系统先预览并校验路径穿越、重复文件、缺失文件和清单字段，再由负责人确认；
- 身份证、签名、银行卡和敏感证件进入敏感资料；
- 页面增加两个清晰入口，不让用户误以为所有文件都必须转换成 Excel；
- 成员导入模板增加学校和目标小团队编号。

### 2.13 公告、知识沉淀和会议回放

反馈问题：

- 希望整理常见问题、计划书/PPT问题、新闻和腾讯会议回放；
- 目前公告如果只显示标题，无法真正作为知识入口。

处理结论：

- 公告列表可以打开正文详情；
- 分类增加通知、常见问题、资料模板、会议回放和新闻；
- 支持附加资源链接；
- 支持直接上传公告附件，资源链接与附件可并存；
- 发布范围区分全实践团队、指定小团队、指定项目和互联网公开；
- 小团队主负责人、共同负责人及获得公告管理权限的核心成员可以发布，不要求老师处理。

### 2.14 操作老师、查看老师和负责人的默认工作视角

第二轮反馈问题：

- 教师看到很多项目时，不能快速判断项目属于哪个小团队、哪场比赛；
- “负责人”既可能是挂名指导人，也可能是实际把事情接下来执行的人；
- 小团队负责人最需要先看到自己团队的人在做什么，而不是先浏览整个实践团队；
- 如果固定页面仍然太杂，需要允许保留个人常用面板。

处理结论：

- 全系统最多只有一个活动的全局“操作老师”，该老师可执行全部业务操作和必要的审批兜底；
- 其他老师保持普通全局角色，在具体团队中标记为“查看老师（只读）”，可查看被授权团队及其下属范围，但不能修改团队、审批或付款；
- 项目清单提供“我的小团队、我管理的、我参与的、全部可见”四个工作视角；
- 普通内部成员、查看老师和负责人默认进入“我的小团队”；操作老师可以直接切换全部可见；
- 可以继续指定某个总团队或小团队筛选，并记住当前视角和筛选，作为个人常用面板；
- 页面分别显示小团队负责人、项目牵头负责人、项目共同负责人、比赛执行负责人，不再只写“负责人”。

### 2.15 项目内“每个人在做什么”

第二轮反馈问题：

- 只显示项目负责人会显得所有工作都由负责人完成；
- 负责人可能只是对外挂名，实际任务由其他同学承接；
- 需要同时看到成员的任务、协作工作、参赛分工和比赛结果。

处理结论：

- 项目清单可展开成员执行摘要；
- 每位活动成员分别显示主责任务数、协作任务数、当前进行中任务及最多三项当前任务标题；
- 同时显示成员参加的比赛和该成员在每场比赛中的具体责任；
- 比赛摘要显示比赛届次、参赛队名称、实际比赛执行负责人、参赛人数和获奖结果；
- 这些数据来自任务和比赛执行记录，不根据项目负责人姓名推断。

### 2.16 比赛贡献与复用

第二轮反馈问题：

- 比赛信息之外，更重要的是哪些人实际参加、分别做了什么；
- 过去项目中的图表、材料或研究结果可能可以直接用于新比赛；
- 复用内容不能导致同一贡献被重复计算。

处理结论：

- 比赛详情按人展示实际参赛状态、比赛角色、具体责任和本比赛贡献；
- 本比赛分工与已审核贡献分开显示，不能把计划分工直接算成有效贡献；
- 可复用区只列出当前参赛成员在查看者可见项目中的记录；
- 只有“审核通过且来源已核验”的记录进入可复用区；
- 复用只引用内容和证明材料，原贡献继续归属来源项目，不自动复制、不重复计分；
- 私密项目中的贡献不会因为同一个人参加了当前比赛而泄露。

### 2.17 经费页面的阅读顺序

第二轮反馈问题：

- 相比一个可能由公式计算的“余额”，负责人更想先看已经花了多少钱；
- 需要直接回答哪个项目、谁经手、花在什么地方、是否报销完成；
- “余额”如果不是银行或学校系统的实时余额，不能让人误以为是真实账户金额。

处理结论：

- 经费首页第一屏先显示待补票据、待审核、待转账、缺付款凭证、部分支付和长期未处理事项；
- 主区默认是项目/比赛双视角追溯表，可逐行打开奖金、票据、审核、付款和时间线；
- “钱花在哪里”按项目—比赛—参赛队列出总额、笔数、经手人、具体用途和报销状态；
- 支出结构按全部已记录支出计算，不只统计已经打款的记录；
- “余额”统一解释为系统计算的可用额度，并展示计算口径；
- 预算、支出结构和计算余额保留在分析区，不再压过资金追溯与待办。

### 2.18 文件夹操作语义

第二轮反馈问题：

- “目录”不清楚是筛选、进入还是文件的真实保存位置；
- 需要明确区分进入文件夹、上传文件和新建文件夹。

处理结论：

- 文件页显示“项目—根目录—当前文件夹”的面包屑；
- 子目录卡片使用“进入”，进入本身不会上传文件；
- 上传按钮写明“上传到当前目录”，弹窗再次展示目标路径；
- 新建文件夹默认建在当前目录，按钮在子目录中改为“新建子文件夹”；
- 全部目录汇总视图中的上传和新建默认使用项目根目录；
- 后端保存并校验文件与所选文件夹的真实关联。

### 2.19 定时报表接收范围

第二轮反馈问题：

- 定时报表是不是每个人都会收到；
- 如果给全团队发送，会不会增加大量日常操作或泄露无权查看的项目。

处理结论：

- 定时报表不默认群发；
- 创建人可以逐个选择接收人，也可以一键选择当前可见团队全员；
- 接收人必须有权查看报表涉及的全部项目，否则不能保存该计划；
- 因此“全员接收”是一次明确选择，不会绕过项目权限。

### 2.20 贡献审核的工作量与可信度

第二轮反馈问题：

- 新成员自报工作后，如果只有负责人审核，可能既累又难判断是否有效；
- 负责人自己的贡献不能由自己确认；
- 又不希望所有负责人、老师或其他团队成员逐级会签。

处理结论：

- 一条手工贡献只分派给一名明确审核人，不走全员逐级审核；
- 每个项目配置审核人池，可以加入共同负责人、其他团队的可信成员或指定老师；
- 普通成员按审核池优先级分派；
- 项目负责人自报贡献时必须分派给独立审核人；
- 贡献人和代填人均不能审核该条记录；
- 审核关注交付物、来源证明和实际效果，不用填报时长替代质量判断。

### 4.1 操作量变化

普通成员不会因为这次改造增加长审批链：

- 日常任务、DDL 和公告阅读仍是直接填写或更新；
- 手工贡献、敏感资料查看和报销只多出一次必要提交；
- 不要求成员补录实际工时，最终只由负责人发布有效工作量占比；
- 普通成员不需要先理解总团队、项目和任务的全部权限配置。

负责人增加的是初始或低频配置，以及每项业务必要的维护，不是把每件事项都送给全部负责人或老师：

- 初次建立总团队和小团队；
- 按项目选择关联小团队、可见范围和贡献审核池；
- 按比赛届次和项目参赛条目维护实际名单，并在结项时发布一次最终工作量；
- 按项目或预算期维护核定预算。

完成这些配置后，普通事项由对应负责人直接处理，不再逐级送给所有核心成员或老师。报销由成员提交、负责人审核、经费经办人带凭证付款；只在超额、跨项目、预算外、学校专项、利益冲突或知识产权流程时进入操作老师兜底。查看老师没有写入、审批或付款权限。

第二轮改造没有给普通成员增加新的固定步骤：

- 项目和比赛执行信息来自原有任务、参赛名单和贡献记录，只是集中展示；
- “我的小团队”是默认视角，负责人无需每次重新筛选整个实践团队；
- 报表全员接收是一个可选的“一键全选”，不是逐人重复添加，也不是默认群发；
- 进入文件夹、上传到当前目录、新建子文件夹分别只有一次明确操作；
- 贡献仍然只需一名无冲突审核人处理，不要求老师或多个负责人串行会签。

### 4.2 明确留到后续的增强项

以下内容不影响本轮小团队基本使用，但仍需单独设计：

- 大额或预算外事项的用款前申请；
- 无冲突手工贡献的批量审核，以及任务验收以外的更多自动证据来源；
- 普通任务“无需验收”开关；当前所有任务仍走统一验收闭环；
- 与学校财务或银行系统的自动对账；当前以票据、流水号和上传凭证作为可审计依据。
