# 团队项目管理平台需求文档 v1.2

## 含：知识产权申请与责任追踪模块、第三方接口预留

---

## 0. 文档定位

本文档用于在团队项目管理平台第一期基础可用版完成后，继续补充后续开发需求。当前第一期已经完成项目、人员、比赛、任务、经费、文件、导入、首页驾驶舱、手机端适配等基础功能，并为贡献、敏感资料、通知、日志、导出等模块预留了架构位置。

后续开发策略保持为：

> 四期完整规划，第一期优先落地，后续按模块逐步增强。

本次新增重点：

1. 暂时不接入飞书，但预留飞书、企业微信、QQ 群机器人、Webhook 等第三方接口；
2. 新增“知识产权申请与责任追踪模块”；
3. 管理软件著作权、专利等成果申请全过程；
4. 记录谁写的、谁申请的、谁修改的、谁确认的；
5. 防止成果撰写人与申请执行人责任不清；
6. 将软著、专利申请工作纳入贡献记录、成员排序和异议处理。

# 一、系统总体方向

## 1.1 系统定位

团队项目管理平台不是单纯的项目表格系统，而是一个长期使用的团队管理、成果沉淀和成员成长平台。

系统需要管理：

- 团队项目；
- 成员信息；
- 比赛进度；
- 任务分工；
- 经费收支；
- 文件资料；
- 成员贡献；
- 成员排序；
- 异议反馈；
- 软件著作权申请；
- 专利申请；
- 敏感资料审批；
- 操作日志；
- 历史项目沉淀；
- 公共成果展示。

核心目标：

```text
项目可追踪
人员可管理
任务可监督
经费可公开
贡献可认定
排序可申诉
资料可审批
申请可追责
操作可审计
成果可展示
历史可沉淀
```

# 二、第三方协作接口预留

## 2.1 当前决策

当前阶段暂时不接入飞书。

原因：

1. 第一阶段系统刚完成，应先保证自建平台稳定；
2. 飞书接入会增加同步、权限、维护复杂度；
3. 当前重点是完成核心业务闭环；
4. 后续是否长期使用飞书，还需要团队实际使用后再决定。

## 2.2 预留原则

虽然暂时不接飞书，但系统要预留第三方接口能力。预留对象包括：

- 飞书；
- 企业微信；
- QQ 群机器人；
- Webhook；
- 邮件；
- 后续其他通知平台。

推荐定位：

```text
自建平台 = 主系统 / 主数据库 / 正式归档 / 权限与审计中心
飞书等工具 = 协作入口 / 表单收集 / 任务提醒 / 群消息通知
```

# 三、知识产权申请与责任追踪模块

## 3.1 模块名称

建议模块名称：

> 知识产权申请与责任追踪模块

前端菜单可以显示为：

> 成果与知识产权 / 软著与专利申请

该模块不是简单记录软著和专利，而是要建立完整责任链。

## 3.2 建设背景

团队后续会涉及软件著作权、专利等成果申请。实际过程中容易出现：

- 有同学说成果是自己写的；
- 但真正去科研处、学校系统或申请平台提交的是另一个同学；
- 如果材料写得不规范、不完整，申请执行人要反复修改；
- 撰写人可能因为“不是我申请”而不认真准备；
- 最终导致申请同学承担额外工作；
- 但系统里无法证明是谁写的、谁申请的、谁修改的。

因此系统需要记录：

```text
谁写的
谁整理的
谁申请的
谁提交的
谁被退回
谁修改的
谁确认的
谁最终归档的
```

核心目标：

> 防止“写的人不负责，申请的人背锅”。

# 四、知识产权申请档案

## 4.1 每个成果独立建档

每一个软件著作权、专利或其他知识产权成果，都需要建立独立申请档案。

成果类型包括：

- 软件著作权；

- 外观设计专利；
- 论文成果；
- 作品著作权；
- 其他科研成果。


# 五、责任分工记录

## 5.1 角色区分

| 角色 | 责任 |
|---|---|
| 主导撰写人 | 对成果内容真实性、完整性、技术描述质量负责 |
| 协作撰写人 | 对自己负责的部分负责 |
| 申请执行人 | 对科研处对接、系统提交、时间节点负责 |
| 材料整理人 | 对身份证、申请表、代码、说明书、签字材料完整性负责 |
| 项目负责人 | 对项目内贡献、成果归属、材料完整性初审 |
| 老师 | 对成果归属、人员排序、最终申请安排确认 |
| 修改责任人 | 对某一次退回问题的修改结果负责 |
| 归档责任人 | 对最终证书、申请文件、受理通知归档负责 |

## 5.2 协作人员表

建议新增模型：

```text
IPApplicationContributor
```

字段建议：

| 字段 | 说明 |
|---|---|
| application | 所属申请 |
| user | 成员 |
| role | main_writer / co_writer / code_provider / document_writer / drawing_provider / tester / executor / material_manager / reviewer |
| contribution_description | 贡献说明 |
| responsibility_description | 责任说明 |
| is_confirmed | 是否确认 |
| confirmed_by | 确认人 |
| confirmed_at | 确认时间 |

## 5.3 责任原则

1. 主导撰写人不能因为不是申请执行人就不负责；
2. 申请执行人负责流程，但不应替撰写人承担全部材料质量问题；
3. 科研处退回后，需要判断责任类型；
4. 如果退回原因属于撰写质量问题，应分配给主导撰写人或对应协作撰写人；
5. 如果退回原因属于提交格式问题，应分配给申请执行人或材料整理人；
6. 实际完成修改的人也应记录为贡献；
7. 所有责任认定和修改记录都应进入日志。

# 六、申请流程

## 6.1 标准流程

```text
创建知识产权申请档案
→ 关联团队项目
→ 确认成果类型
→ 确认主导撰写人
→ 确认协作撰写人
→ 确认材料整理人
→ 上传初版材料
→ 项目负责人审核
→ 老师确认
→ 确认申请执行人
→ 申请执行人提交科研处 / 申请平台
→ 科研处或平台反馈
→ 如被退回，记录退回原因
→ 分配修改责任人
→ 修改后重新提交
→ 受理 / 授权 / 登记完成
→ 上传证书和最终材料
→ 归档到项目成果
→ 同步到成员贡献记录
```

## 6.2 前端步骤条

建议前端使用步骤条展示：

```text
基础信息
→ 责任分工
→ 材料上传
→ 负责人审核
→ 老师确认
→ 科研处提交
→ 退回与修改
→ 受理 / 授权
→ 成果归档
```

# 七、退回修改责任记录

## 7.1 退回记录表

建议新增模型：

```text
IPReturnRecord
```

字段建议：

| 字段 | 说明 |
|---|---|
| application | 所属申请 |
| return_time | 退回时间 |
| return_source | research_office / school_system / agency / patent_platform / other |
| return_reason | 退回原因 |
| responsibility_type | writing_problem / material_problem / submit_problem / review_problem / system_problem / unattributable / other |
| responsible_user | 责任人 |
| assigned_by | 分配人 |
| modify_deadline | 修改截止时间 |
| actual_modifier | 实际修改人 |
| modify_description | 修改说明 |
| result | pending / modified / resubmitted / accepted / rejected |
| proof_file | 证明材料 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

## 7.2 退回原因分类

| 分类 | 说明 |
|---|---|
| 技术内容不清 | 技术方案描述不完整、不准确 |
| 格式问题 | 格式、模板、命名、排版不符合要求 |
| 代码问题 | 软著源代码不完整、不规范 |
| 说明书问题 | 软件说明书、专利说明书逻辑不清 |
| 权利要求问题 | 专利权利要求书不规范 |
| 图纸问题 | 附图、流程图、结构图不符合要求 |
| 身份材料问题 | 身份证、签字、申请人信息有误 |
| 排序问题 | 申请人排序或署名信息有争议 |
| 提交流程问题 | 系统提交、科研处流程操作不规范 |
| 其他问题 | 其他原因 |

## 7.3 退回修改原则

1. 每次退回必须创建退回记录；
2. 退回记录必须填写退回原因；
3. 必须明确责任类型；
4. 必须指定修改责任人；
5. 必须记录实际修改人；
6. 实际修改人可与责任人不同；
7. 实际修改工作应同步为贡献记录；
8. 多次退回应累计次数；
9. 所有退回记录不可物理删除，只能作废或更正；
10. 老师和管理员可以查看完整退回记录。

| 软著退回修改贡献 | 处理科研处退回、修改说明书或代码材料 |
| 专利撰写贡献 | 完成交底书、说明书、权利要求书、图纸等 |
| 专利申请执行贡献 | 负责专利提交、代理机构对接、科研处流程 |

## 9.2 同步规则

```text

→ 进入贡献档案
```

关键事件包括：

- 成员被确认为主导撰写人；
- 成员上传关键材料；
- 成员完成科研处退回修改；
- 成员完成重新提交；
- 成员完成最终归档；
- 成员作为申请执行人完成流程对接。

# 十、与成员排序和异议机制联动

## 10.1 排序依据

知识产权申请贡献应纳入项目成员排序依据。排序时不能只看谁是第一申请人，也要看：

- 谁写了材料；
- 谁整理了源代码；
- 谁写了专利交底书；
- 谁跑了科研处；
- 谁处理了退回修改；
- 谁完成最终归档。

## 10.2 异议机制

异议场景包括：

1. 成员认为自己实际撰写但未被记录；
2. 成员认为某人只是挂名但排在前面；
3. 申请执行人认为退回修改工作未被记录；
4. 成员认为退回责任分配不合理；
5. 成员认为成果排序不公平；
6. 成员认为材料撰写人和实际贡献不符。

流程：

```text
成员查看知识产权申请档案
→ 发现贡献、责任或排序问题
→ 提交异议
→ 上传证明材料
→ 项目负责人初审
→ 老师最终确认
→ 系统记录最终处理结果
```

可见范围：

```text
团队成员可见
```

# 十一、敏感资料联动

## 11.1 敏感资料范围

软著 / 专利申请可能涉及：

- 学生身份证号；
- 老师身份证号；
- 身份证正反面图片；
- 手机号；
- 通讯地址；
- 签字材料；
- 个人身份证明；
- 其他申请资料。

这些信息必须走敏感资料审批机制。

## 11.2 查看流程

```text
登录系统
→ 进入敏感资料申请页面
→ 选择申请对象
→ 选择调用资料类型
→ 填写申请理由
→ 填写使用场景：软著 / 专利申请
→ 提交申请
→ 审批人审核
→ 审批通过后限时查看
→ 系统记录每一次查看、下载、导出
→ 权限到期自动关闭
```

知识产权申请档案中只显示：

```text
身份证资料：已存在 / 未完善 / 需申请查看
```

不直接显示完整身份证号。

| 项目负责人 | 创建和维护本项目申请、分配责任、审核贡献、初审异议 |
| 申请执行人 | 维护申请状态、提交记录、科研处反馈、退回修改 |
| 主导撰写人 | 上传和修改自己负责的材料 |
| 普通项目成员 | 查看本项目申请记录、提交贡献、提出异议 |
| 敏感资料审批人 | 审批身份证等敏感资料调用 |
| 公共访客 | 无权限查看内部申请内容 |
